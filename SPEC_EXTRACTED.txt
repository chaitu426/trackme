
Growth Intelligence Platform
Production Build Specification for a Coding Agent
Implementation target: Next.js + TypeScriptVersion 1.0 | 16 September 2026
Purpose and directive
Build a multi-tenant, privacy-first growth intelligence SaaS. It must let a customer install a small tracking snippet, view accurate website analytics in real time, define conversions, connect billing data, understand which acquisition sources generate revenue, receive proactive alerts, and export its data. The product must be production-ready in design, but delivery should be phased so the team validates demand before building enterprise complexity.
This is not a request to clone any platform’s proprietary source code, visual identity, or wording. Use the named platforms only as public product and architectural references. Implement original UI, original workflows, and an independently designed data model.

Core thesis
The platform should win by combining the simplicity of a privacy-first website analytics product with a trusted growth decision layer: acquisition -> activation -> subscription revenue -> retention. Basic pageview dashboards are commoditized. The durable advantage is clear attribution, transparent measurement quality, actionable alerts, data ownership, and lightweight product analytics without enterprise complexity.

Product principles
Privacy by default: no cookies required for basic measurement; minimize IP handling; never capture form contents, passwords, payment data, email addresses, or arbitrary PII by default.
Trust before cleverness: every chart must define its metric, date range, timezone, filters, data freshness, and attribution model.
Fast time to value: customer should install the snippet and see verified traffic in under five minutes.
Progressive complexity: simple overview first; advanced segmentation, attribution, exports, and product analytics are available only when useful.
Data ownership: customers can export permitted data and use a stable API; do not create artificial lock-in through inaccessible data.
Reliable AI: the AI interface may only answer from executed, validated analytics queries and must expose the applied query/filters.

Architecture references
Use two reference patterns, then implement the optimized hybrid described below. Plausible’s documented/self-hosted pattern separates operational data in PostgreSQL from high-volume analytics events in ClickHouse. PostHog’s commonly documented production pattern adds a durable streaming layer (Kafka-compatible queue), uses ClickHouse for analytics, PostgreSQL for application data, and Redis for caching/realtime coordination. ClickHouse itself is an OLAP-oriented columnar database designed for high-performance analytical workloads. [web:17][web:18][web:19][web:22][web:23][web:24]
Reference pattern
Strength
Use in our product
Plausible-style: app + PostgreSQL + ClickHouse
Operational simplicity and correct separation of transactional vs event workloads.
Use for local development and early production when event volumes are modest.
PostHog-style: ingestion + Kafka/Redpanda + ClickHouse + PostgreSQL + Redis
Backpressure, replayability, decoupled transforms and scale.
Adopt progressively as production volume/reliability needs grow; design interfaces so queue insertion can be enabled early.
ClickHouse analytical core
Fast scans, aggregations and event-oriented storage.
Primary store for immutable events, rollups, funnels and dimensional reports.
Final target architecture
Implement a modular monolith for the control plane and dashboard, with an isolated ingestion pipeline. Do not begin with dozens of microservices. Use clean boundaries, queues, typed contracts and independently deployable workers so the system can evolve into a distributed architecture without a rewrite.

Event pipeline
Step
Design
Capture
Tracker assigns anonymous session ID and rotating visitor pseudonym; captures only approved dimensions and event properties.
Batch
Buffer a small number of events or a brief interval; use navigator.sendBeacon on unload when available.
Receive
Ingestion endpoint verifies site key, origin policy, payload size, schema version, event UUID and rate limits.
Sanitize
Reject or redact suspected PII keys/values; normalize URL; remove query parameters by default except approved campaign keys.
Enrich
Derive country/region from IP at edge; parse user agent; normalize referrer/UTM; apply bot decision. Do not retain full IP unless a reviewed, explicit legal requirement exists.
Queue
Write accepted events to a durable stream. Respond quickly; do not synchronously execute expensive queries.
Process
Consumer batches inserts into ClickHouse; tracks failures; retries safely using event UUID/idempotency.
Aggregate
Materialized views and scheduled rollups generate hourly/daily metrics and Web Vital percentiles.
Serve
Dashboard/API reads aggregate tables for common views; raw events only for tightly bounded drill-down queries.
Alert
Scheduled/anomaly worker compares current data with historical baseline and sends actionable notifications.

Privacy and security requirements
Use HTTPS only. Configure CSP, secure headers, CSRF protection where applicable, input validation, rate limiting, and WAF/CDN protections.
Hash API keys; display their plaintext only once. Encrypt third-party integration secrets using managed KMS/envelope encryption. Rotate and revoke keys.
Use row/tenant isolation at the application layer. Every database query must receive workspace/site scope from the verified session/token, never solely from client parameters.
Do not allow unrestricted event property names/values. Enforce maximum payload sizes, depth limits, allowlists for key categories, and PII detection/redaction.
Provide retention controls, deletion jobs, export capability, DPA/subprocessor documentation, audit logs, and an incident-response runbook before scaling privacy claims.
Never claim universal legal compliance solely because tracking is cookieless. Obtain professional legal review for GDPR, UK GDPR, CCPA/CPRA, PECR/ePrivacy and each target jurisdiction.
Next.js implementation conventions
Area
Required convention
Language
TypeScript with strict mode enabled. Avoid any; share API/types through a package or lib module.
Rendering
Use Next.js App Router. Prefer React Server Components for initial dashboard data; client components only for interactive charts, filters, streaming realtime updates and forms.
Routes
Use route groups such as /(marketing), /(auth), /(app). Keep public dashboard routes isolated, e.g. /share/[slug].
Data access
Keep database access in server-only modules. Use a typed query/service layer; do not query databases from browser components.
Validation
Use Zod schemas at every API boundary, tracker payload boundary, form action and integration webhook boundary.
Charts
Use a production-quality React chart library. All charts require loading, empty, error, comparison, timezone and accessible text states.
State
Keep filters/shareable query state in URL search params. Use server actions/route handlers deliberately; do not hide business logic in UI components.
Testing
Unit test metric calculations and validation; integration-test API auth/tenant boundaries; end-to-end test tracker installation and dashboard flows.
Styling
Tailwind CSS with design tokens. Build an original clean B2B interface; do not duplicate competitor layouts.
Errors
Use error.tsx, loading.tsx, not-found.tsx, structured error codes and correlation IDs. Never surface secrets in client errors.

Non-functional requirements
Requirement
Target
Tracker payload
Keep initial tracker very small; target < 2 KB gzip excluding optional Web Vitals module where possible.
Ingestion response
Fast acknowledge path; target p95 under 200 ms in primary region under normal load.
Dashboard performance
Common aggregate reports target p95 under 1.5 seconds; cache safe repeated queries.
Freshness
Realtime visible within seconds; non-realtime aggregates fresh within a documented short interval.
Availability
Design for graceful degradation: if realtime fails, historical analytics remains available; if queue is delayed, show freshness state.
Accuracy
Idempotent writes; explicit bot/filter rules; transparent metric definitions; automated synthetic event checks.
Accessibility
Keyboard navigable dashboard, semantic labels, sufficient contrast, text alternatives for charts.
Cost controls
Event quotas, payload restrictions, TTLs, rollups, query guardrails, per-tenant usage monitoring and export limits.

Definition of done
Feature has written user story, acceptance criteria, privacy impact check, observability metrics, error states, loading/empty states, and tests.
No cross-workspace data access is possible through UI, API, exports, cache keys, background jobs or public dashboard links.
All tracker and API payloads are versioned and validated.
All production secrets are stored in a managed secret store; no secrets are committed or sent to the browser.
Dashboard values can be traced to documented query definitions and filtered data.
Each release has migration/rollback guidance and a monitored deployment path.
